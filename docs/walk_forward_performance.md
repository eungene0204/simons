# 워크포워드·최적화 성능 메모 (2026-08-19)

워크포워드(WFA)와 파라미터 최적화의 실행 시간을 어디서 어떻게 줄였고, 다음 단계로 무엇이 남았는지
기록한다. 규제·기능 요구는 `docs/SRS.md` FR-BT-049c, 구현 위치는 `docs/software_architecture.md`.

## 1. 실측 — 시간은 어디에 쓰이나

기준: KOSPI200 200종목, 5Y, RSI 진입/청산 + 손절, 로컬 맥(10코어).

| 단계 | 백테스트 1회 | 비중 |
|---|---|---|
| Phase1 — 종목별 로드·워밍업 절단·지표(stockstats)·리졸버·기간 필터·전처리(수정주가·정합) | 4.7s | **97%** |
| Simulator — 파이썬 루프(의도) + vectorbt from_orders(체결) | 0.04s | 1% |
| Format — 결과 정리 | 0.10s | 2% |
| (부가) 리밸런싱 6주기 비교 — 결과 화면 탭용 재시뮬레이션 | 0.8s | 시뮬레이터의 20배 |

Phase1 안에서는 지표(stockstats) ≈ 전처리 ≈ 반반. 로드는 캐시 후 0.

**스레드는 안 빨라진다.** Phase1 종목별 스레드풀을 1·3·6·14개로 바꿔도 5.4~6.5s로 같다 — GIL에
묶인 pandas/파이썬 코드라 코어를 못 쓴다. 병렬 자원은 **프로세스**뿐이다.

## 2. 한 것

### 2-1. 재계산 제거 — 최적화 세션 Phase1 캐시 (`engine/prep_cache.py`)

- 최적화(그리드·베이지안)와 WFA는 같은 날짜 범위에서 파라미터만 바꿔 백테스트를 수십 회 반복한다.
  손절·익절·보유종목수·리밸런싱 주기는 Phase1에 영향이 없고, RSI 임계값 같은 값도 지표 컬럼을 바꾸지 않는다.
- `BacktestEngine.optimization_session()` 동안 종목별 Phase1 산출물을
  `(종목, 워밍업 시작일, 기간 경계, 배당 옵션, 구조 파라미터만 남긴 조건 서명)` 키로 재사용한다.
  구조 파라미터 = 지표 컬럼을 결정하는 기간류(`STRUCTURAL_PARAM_KEYS`) — `IndicatorEngine`·`DataResolver`가
  params에서 읽는 이름을 소스 스캔 테스트가 대조한다.
- 세션 안에서는 결과 화면 전용 리밸런싱 6주기 비교를 만들지 않는다(적중 시 남는 시간의 절반).
- **결과는 바이트 단위 동일**(`tests/test_prep_cache.py`가 on/off 비교). 적중 시 Phase1 5~7s → 0.25~0.4s.
- 예산 `BACKTEST_PREP_CACHE_MB`(기본 2048, LRU). 세션은 요청 간에 살아남지 않는다.

### 2-2. 창 단위 프로세스 병렬 (`engine/wfa_workers.py`)

- 창은 독립(각 창 = IS 최적화 + OOS 검증). spawn 프로세스 풀로 흩뿌린다. 워커마다 엔진을 따로 만들므로
  엔진 공유 상태(warnings 등) 경합이 없다. 옵튜나 시드가 고정이라 **병렬 결과 = 순차 결과**(`tests/test_walk_forward_parallel.py`).
- 워커 기동(spawn + vectorbt·pandas import ≈ 5~9s)은 '기간 확인' 백테스트와 겹치도록 선기동.
- 진행률은 mp.Queue → 부모 합산(`windows_done/trials_done/workers/active_windows`), 취소는 mp.Event 협조적.
- 워커의 Phase1 스레드는 코어÷워커(최대 4)로 낮춘다 — 3워커에서 스레드 14개 53s → 2개 34s.
- `WALK_FORWARD_WORKERS` 기본 min(cpu−1, 8, 창 수). 2 vCPU 박스는 자동 순차.

### 2-3. 결과 (3창 × 30시도, KOSPI200 5Y, 로컬 맥)

| 구성 | 벽시계 |
|---|---|
| 원래(캐시 없음, 순차) | ≈ 450s (4.8s × 94회 추정; 19회 실측 99s와 일치) |
| 캐시, 순차 | 64s |
| 캐시 + 3워커 | 49s |
| + Phase1 프로세스 풀(창 워커당 3) | **30s** |

병렬 이득이 작아 보이는 이유: 창마다 피할 수 없는 첫 계산(IS 첫 시도 1회 + OOS 1회 ≈ 10s)이 남고 창이 3개뿐이다.
창이 많고 코어가 많을수록 창 수에 비례해 줄어든다.

### 2-4. Phase1 프로세스 풀 (`engine/phase1.py`, `engine/phase1_pool.py`) — 모든 백테스트

- 종목별 파이프라인을 순수 함수(`process_symbol`, ctx 입력·부수효과 반환)로 추출해 스레드 경로와 프로세스 경로가
  같은 코드로 돌게 했다. 상주 spawn 풀(기동 1회), 결정적 샤딩(crc32 % n)으로 워커별 parquet·세션 캐시가 겹치지 않고
  같은 종목은 늘 같은 워커에 적중. 세션 open/close 브로드캐스트, 부모 사망 감지, 워커 사망=오류+재기동.
- 단일 백테스트(KOSPI200 5Y): 3.9s → 1.6s(4워커) → 1.3s(8워커). 남는 1.3s의 60%는 결과 화면용 리밸런싱 6주기 비교(0.8s).
- 워크포워드 창 워커 안에서는 코어÷창워커 크기로 중첩(총 프로세스 ≤ 코어).

### 2-5. 리밸런싱 6주기 비교(FR-BT-064) — 워커 선제출 + 1회 계산 복제

- 결과 화면 전용 재시뮬레이션(6주기)이 단일 백테스트 잔여 시간의 60%(0.8~1.0s: 시뮬 0.5 + vectorbt 통계 0.5)였다.
- 시뮬레이션 직후 입력 프레임을 Phase1 풀 워커에 **선제출**해 메인 결과 정리(Format)와 겹쳐 돌리고, 조립 지점에서
  행만 받는다(`Phase1Pool.submit_rebalance_rows` → `RebalanceRowsJob.result`). 워커 실패 시 동기 경로로 재계산.
- 보유 상한이 없어 시뮬레이터 `rebalance_mode`가 어떤 주기에서도 False인 전략은 6번이 같은 결과이므로
  **1회만 돌리고 6행 복제**(`periods_to_simulate`/`assemble_comparison`) — 결과 동일, 시간 1/6. 이는 풀이 없는 2 vCPU에서도 적용.
- 단일 백테스트(KOSPI200 5Y, 8워커): 1.3s → **0.9~1.0s**(비교 대기 ≈ 0). 동기 경로·풀 경로 비교표 동일(`test_phase1_pool.py`).

### 2-6. 안전장치 — 결과 동일성 게이트 (`scripts/qa_backtest_equivalence.py`)

- 실제 데이터로 28개 전략(지표 13종·재무 필터·랭킹/리밸런싱 5종·분위 그룹·상한 없음·배당·명시 기간·KOSPI200 PIT·ETF·섹터·단일 종목)을
  네 경로(기준 / 세션 2회 / 풀 / 풀+세션 2회)로 돌려 거래·자산곡선·지표·경고·비교표를 바이트 단위로 대조한다.
  `--wfa`면 워크포워드 순차/병렬 창도 대조. 불일치가 하나라도 있으면 종료 코드 1.
- 성능 경로(위 모듈)를 고치면 반드시 돌린다(CLAUDE.md 필수 규칙). 유닛 테스트(합성 데이터)와 달리 실데이터의
  결측·상폐·펀더멘털 리졸버·ETF 마스터까지 지나가므로 유닛 테스트가 못 보는 차이를 잡는다.
- 구조 파라미터 화이트리스트 스캔(`test_prep_cache.py`)은 `p.get/p[]/params.get/params[]/cond['params'][]` 문법을 모두 본다.

## 3. GPU는 왜 안 되나

- Phase1은 "작은 pandas 계산 × 종목 수"다. GPU는 큰 행렬 한 방에 강하고 작은 계산 수천 번은 커널 왕복에 먹힌다.
  stockstats는 pandas 전용이라 GPU(cuDF/CuPy)로 옮기려면 지표 계산을 다시 써야 한다.
- 시뮬레이터는 날짜순 파이썬 루프 + numba(CPU). GPU 백엔드가 없고 순차 의존이라 GPU에 안 맞는다.
- GPU가 먹히는 부분은 AI 모델 추론뿐인데 WFA 병목이 아니다.
- 지표 계산을 "날짜×종목 패널 행렬 연산"으로 재작성하면 GPU 자리가 생기지만, 그 재작성만으로 CPU numpy에서도
  이미 크게 빨라진다 → GPU는 그 다음 선택지.

## 4. 남은 지렛대 (미착수)

1. **Format(결과 정리) 0.4s + Phase1 풀 왕복(피클) 0.4s** — 이제 단일 백테스트 잔여의 대부분. Format은 vectorbt
   Portfolio 통계 래퍼 비용, 풀 왕복은 종목별 결과 패키지(시계열 10개) 피클. 둘 다 결과 불변 최적화 여지 있음.
2. **stockstats 교체** — 지표(RSI·MA·EMA 등)를 numpy 벡터화로 직접 계산. 결과값 동일성 검증이 필요(엔진 버전 규칙).
3. **Modal CPU 오프로드** — 이미 LLM용으로 쓰는 Modal은 GPU만이 아니라 CPU 코어 수십 개 컨테이너를
   초 단위 과금·scale-to-zero로 준다. 창을 Modal 함수 `.map()`으로 흩뿌리면 박스 스펙과 무관하게 병렬이 된다.
   조건: (a) parquet(`data/ohlcv`, 펀더멘털 캐시)을 Modal Volume에 미러(야간 21:00 스케줄과 동기), (b) 워커 이미지
   (backend 코드 + requirements, CPU torch), (c) 진행률/취소를 Modal 함수 호출 경계로 옮김(창 단위 진행만 가능),
   (d) 콜드스타트(이미지 로드 수십 초). WFA처럼 산발적이고 큰 부하에 맞고, 상시 GPU 박스보다 싸다.
   구현 여부는 인프라 결정(데이터 미러·이미지·과금)이라 사용자 판단으로 남긴다.
4. free-threaded 파이썬(3.14t)은 numba(vectorbt)·pandas 지원이 확정되기 전에는 대상이 아니다 — 프로세스 병렬이 같은 효과를 지금 낸다.
