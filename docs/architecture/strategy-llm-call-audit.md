# 전략 해석 LLM 호출 절감 조사

조사일: 2026-09-24. 아래 내용은 구현 전 조사 기록이다.
후속 승인으로 네 가지 호출 절감을 구현했다. [구현·검증 결과](../development/strategy-call-reduction.md)를 참조한다.
통계적인 품질/지연 A/B는 미실행이며, 회귀 테스트와 현재 모델의 소수 실호출 표본으로 검증했다.

## 작업 명세

- **Task:** 동일 전략의 LLM 호출 경로와 품질을 보존할 절감 방안을 조사한다.
- **Boundary:** G — Governance / Policy Docs.
- **Files allowed:** 이 문서, `docs/PROJECT_PLAN.md`.
- **Do not:** 실행 코드·환경 설정·모델·API·DB를 변경하거나 자연어 해석을 정규식으로 대체하지 않는다.
- **Requirements:** 코드와 로컬 trace를 구분해 근거를 남기고, 기존 최적화·추가 후보·품질 검증 조건을 정리한다.
- **Run:** 로컬 JSONL의 중첩 span을 읽기 전용 집계하고 `git diff --check`를 실행한다. 문서 변경이므로 단위 테스트는 불필요하다.
- **Deliver:** 작은 문서 diff와 조사 결과. 절감 목표를 검증된 효과로 표현하지 않는다.

## 결론

줄일 수 있다. 우선순위는 (1) 기존 캐시의 정확성과 동시 요청 중복 제거,
(2) 보조 추출·검사 호출 통합, (3) 구조화된 해석 결과로 해결 가능한 planner 작업 축소다.
단순 전략의 초기 파스는 **2회(본 해석 1 + 독립 보조 검사 1)**를 실험 목표로 삼을 수 있다.
별도 의도 분류가 있는 UI 경로는 합계 3회다. 복잡한 테마 검색·의미 모호성·복구는 추가 호출을 허용한다.
이 목표의 품질 유지 여부는 아직 검증하지 않았다. 모든 요청을 무조건 1회로 제한하는 방안은 채택하지 않는다.

## 이미 구현된 최적화

- **완성 결과 캐시:** `backend/main.py:3892`에서 파스 전체를 건너뛴다. 프로세스 메모리 최대 200개이며
  원문·이전 전략·질문·지역·프롬프트 버전·일자·일부 유니버스 파일 stamp를 키로 사용한다(`backend/nl_cache.py`).
  동일 전략이라도 문맥/일자가 다르거나 재시작·다른 worker·축출이 있으면 미적중할 수 있다. 단순 캐시 신설은 중복 작업이다.
- **병렬 실행:** OpenRouter에서는 planner-first·본 해석·조건 구절 추출을 병렬로 실행한다. 호출 횟수 자체는 줄지 않는다.
- **칩과 질문 큐:** `run_chip_answer`, `_next_ask_from_queue`가 기존 구조화 선택과 질문을 재사용한다.
  큐가 없고 공백이 남으면 planner 재계획이 붙을 수 있다(`primary.py:4027`, `primary.py:5261`).
- **도구 캐시:** DAG의 `call_cache`는 파스 1회 내 도구 중복을 막는다. 턴 간 전역 LLM 결과 캐시와는 다르다.
- **검증:** `validate_intent`·`compile_strategy`는 결정론이다. UI의 전략 검증도
  `backend/api/coach_routes.py:54`의 validation 모드와 `StrategyValidationAgent`를 사용하므로 LLM 절감 대상으로 계산하지 않는다.
  레거시 파서의 후행 LLM 검증을 primary 경로의 상시 호출로 세어서도 안 된다(`backend/main.py:4071`).

## 적용 후보와 품질 조건

### 1. 완전히 동일한 요청을 묶고 캐시 문맥을 보완

진행 중인 동일 요청은 하나의 계산을 공유(singleflight)하고 완료 결과를 재사용한다.
현재 캐시 조회/저장 사이에 이런 합류 장치는 없다. 동시에 N건이 들어올 때 중복 파스를 N→1로 줄이는 목표다.
처음 들어온 단일 요청의 호출 수는 줄지 않는다. 한 구독자의 취소가 다른 구독자를 취소하지 않아야 한다.

먼저 캐시 키를 감사한다. 전체 응답은 `previous_explicit_fields`, `previous_declined_fields`, 이전 artifact/field 상태에도
영향받는데 현재 키에는 없고, 실제 provider 모델·보조 프롬프트·기능 플래그·테마 지식 버전도 충분히 반영되지 않는다.
불변 해석 결과만 캐시하고 요청별 메타데이터는 재계산하거나, 모든 결과 의존성을 키에 포함해야 한다.
실패·취소·부분 결과는 성공 캐시로 굳히지 않는다. 의미 유사도만으로 다른 숫자/부정을 가진 전략을 재사용하지 않는다.
의도 분류는 별도 호출이므로 파스 캐시 적중만으로 전체 UI가 0회가 되는 것은 아니다.

### 2. 독립 보조 추출 및 조건 판정 통합

첫 실험은 조건 구절 추출 결과에 백테스트 기간과 그 인용을 함께 싣는 방식이다.
별도 기간 회수 1회를 없앨 수 있으며, 원문만 받는 보조 추출은 본 해석과 병렬 실행을 유지할 수 있다.
조건 나열 과제를 복잡하게 하면 기존 recall이 떨어질 수 있다. 특히 현 코드 주석은 과제 간 간섭 때문에
기간 추출을 분리했다고 명시하므로, 프롬프트 병합만 하고 품질 유지를 가정해서는 안 된다.

다음 실험은 인용 대조·거래대금·적립식 판정을 대상 배열과 고정 ID를 가진 하나의 verifier로 묶는 것이다.
기존 검사별 허용값·출처 대조·덮어쓰기 금지·실패 시 처리 정책을 보존한다. 회수된 조건까지 검증 순서를 재설계해야 한다.
원문 기반 누락 검사는 본 해석과 독립성을 유지한다. 본 해석 모델의 자기 확신만으로 검사를 생략하지 않는다.
`contribution_plan_check.applies_to`가 모든 미지원 표현까지 받는 넓은 조건도 통합 verifier의 비용 절감 후보다.

### 3. 단순 유니버스와 고정 질문의 planner 호출 축소

인터프리터와 독립 보조 추출이 유니버스 표현을 빠짐없이 내고, 정본 조회가 단일 결과로 종결되는 경우
planner의 다음 행동 생성 없이 기존 도구·검증·슬롯 질문을 실행한다. 미해결/다의적 테마에만 planner를 남긴다.
본 해석의 유니버스가 비어 있다는 이유만으로 planner를 끄면 안 된다. planner-first는 과거 '보안주' 누락을 막기 위해 생겼다.
보조 추출의 유니버스 회수까지 검증하거나 독립 유니버스 추출을 유지한 뒤에 게이트를 적용해야 한다.

또한 도구 결과가 다음 조회를 유일하게 결정하는 구간은 코드로 연결하고, 의미 선택이 남은 곳만 LLM에 맡길 수 있다.
기존 자동 후속 조회와 call_cache를 재사용한다. 칩 답변 뒤 단순한 다음 빈 슬롯 질문도 같은 원칙을 적용한다.
자유 입력의 뜻을 정규식으로 분류하거나, 테마를 임의의 업종/종목으로 확정하는 방식은 제외한다.

### 4. 의도 분류와 전략 해석 통합은 후순위

한 응답에 라우팅 의도와 StrategyIntent를 함께 받아 초기 요청에서 1회를 절감할 수 있다.
다만 분류기는 전략 외 질문·취소·현재 전략 상태·대화 이력도 해석한다. 모든 입력에 큰 전략 프롬프트를 사용하면
오히려 지연과 토큰이 늘 수 있다. 두 계층의 문맥과 정책을 보존하는 별도 실험으로 다룬다.

## 품질 검증 및 구현 순서

1. 로컬 trace 집계 → 완전 동일 요청의 캐시 키/동시 합류 → 보조 추출 통합 → planner 축소 순으로 단계별 적용한다.
2. 현재 모델/provider를 고정하고, 단순 재무·이동평균/신고가·거래대금 평균 비교·조건 다중 나열·기간 부재/명시·
   적립식·미지원 개념·모호 테마·수정/칩·KR/US·숫자/부정만 다른 문장에 대해 기존/후보를 반복 비교한다.
3. 정답은 문구 일치가 아니라 조건·연산자·값·기간·유니버스·누락/미지원·필요한 되묻기·사용자 거부 상태다.
   지원하지 않는 개념의 조용한 대체, 조건 유실, 임의 기본값 확정에 새 회귀가 없어야 한다.
4. 캐시 미적중/적중/동시 요청을 분리해 논리 호출 수, 실제 전송 시도, 토큰, p50/p95 지연, fallback/오류를 측정한다.
   소수 예시나 스텁 테스트 통과만으로 LLM 품질 동등성을 선언하지 않는다.
5. 후속 backend 변경 시 `uv run pytest backend/tests` 전체 통과가 필요하다. 프론트까지 변경하는 별도 작업은
   `npm run test:frontend`도 실행한다. 관련 기존 회귀는 `test_strategy_conversation.py`, `test_nl_cache.py`,
   `test_parallel_parse.py`, `test_planner_first.py`, `test_dag_planner.py`, `test_chip_answer.py`, `test_intent_interpreter.py`다.

현재 boundary 문서는 `backend/strategy_conversation/**`, `backend/nl_cache.py`, 의도 분류 경로를
하나의 구현 boundary로 포괄하지 않는다. 구현 착수 전 G boundary 작업으로 소유 경계를 명확히 하고,
캐시/보조 검사/planner/분류 통합을 각각 3~5파일의 작업으로 나눈다.
`docs/software_architecture.md`와 `docs/SRS.md`도 검토했으며, 이번에는 동작 변경이 없어 조사 문서와 프로젝트 계획만 갱신한다.
