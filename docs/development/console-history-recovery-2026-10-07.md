# Console 과거 사용 이력 대조·복구 — 2026-10-07

## 범위와 대상

사용자가 승인한 Console Usage History 범위의 후속 DB 대조·복구다. 배포 문서에 기재된 운영 Supabase 프로젝트와 현재 DB 설정이 일치함을 확인했다. 애플리케이션 배포·스키마 변경은 수행하지 않았다.

- 전체 사용자 42명, 게스트 21명
- Q&A 원본 1,170건, 대화 스냅샷 77개, 사용자 저장 결과 133건
- 스냅샷의 완료 응답 288건, 미완료 응답 4건
- 관리자 사용량 조정/플랜 변경 감사 로그 0건

|---|---:|---|

사용자 12명의 기록이 보완됐으며 Q&A는 1,174건이 됐다. 기존 1,170건의 본문·사용자·기록 시각은 변경하지 않았다. 카드가 이미 있던 기록은 덮어쓰지 않았다. 사용자 카운터, 로그인 시각, 저장 결과 연결도 변경하지 않았다.

복구된 카드에는 `recovery.source=StrategyChatLog`, 원본 스냅샷 ID·저장 시각·내용 해시·복구 시각을 남겼다. 새 Q&A 4건은 `qa-recovered-v1-` 접두사의 결정적 ID를 사용한다. 정확한 턴별 시각은 원본에 없으므로 `createdAt`에는 **대화 스냅샷 저장 시각**을 사용했고 `latencyMs`는 null로 유지했다. 새 조회 코드와 UI는 이를 복구 기록으로 구분하며 카드 출처도 `chat_snapshot`으로 표시한다. **이 표시 변경은 코드 배포 후 반영된다.**

## 적용 안전성과 검증

- 읽기 전용 Repeatable Read로 대조 자료를 보관했다.
- 쓰기 직전에 실 DB를 재조회해 복구 계획과 동일함을 검증했다.
- 보정 트랜잭션 동안 Q&A 쓰기와 해당 스냅샷 수정을 잠시 직렬화했다. 잠금 대기는 3초로 제한했다.
- Q&A 4건 추가와 빈 카드 109건 보완을 한 트랜잭션으로 수행했다. 건수·원본 보존 검증 실패 시 전체 롤백하도록 실행했다.
- 커밋 이후 **새 DB 연결**로 다시 읽어 동일 검증을 수행했다. 복구 계획 재계산 결과 **추가할 응답 0건, 보완할 카드 0건**이다.
- 전체 프론트 테스트: `npm run test:frontend` — 324개 파일, **2,388건 통과 / 1건 건너뜀**. 이번 단계 회귀 7건 추가.
- 변경 파일 `next lint` 및 `git diff --check` 통과. 후속 `npm run build`도 통과했다(첫 시도는 Next.js 페이지 목록 수집 오류, 재시도 성공). 빌드 중 시장지수 API의 외부 연결은 샌드박스에서 `EPERM`을 보고했으나 빌드는 완료됐다.
- `npx tsc --noEmit --incremental false`는 앞선 작업과 동일하게 수정하지 않은 테스트 파일 4곳의 타입 오류로 실패했다. 이번 단계 변경 파일의 타입 오류는 보고되지 않았다.

## 복구하지 않은 항목

- 백테스트 카운터는 요청 기준이며 누적 카운터 도입일(2026-09-30)과 사용자별 사용량 주기가 다르다. 저장 결과는 실행 원장이 아니므로 월 사용량과 누적 횟수가 다르다는 이유로 조정하지 않았다. 누적 횟수와 마지막 요청 시각의 유무가 모순되는 사용자는 없었다.
- 실행 건별 원장이 없어 과거 동시 요청에서 누락된 월 카운터를 정확히 계산할 수 없다. 횟수·시각을 추정 보정하지 않았다.
- 미완료 응답 4건, 같은 세션의 스냅샷이 없는 비로그인 기록 17건은 변경하지 않았다.
- 원본에 동일 사용자·세션·턴·질문·답변의 중복 1쌍이 있었지만 발생 의도를 확정할 자료가 없어 삭제하지 않았다.
- 사용자별 대화 스냅샷은 최근 30개로 제한된다. 이미 제거된 스냅샷·브라우저에서 서버로 오지 않은 내용은 복구하지 못한다. 남은 대상 0건은 **현재 보존된 근거에서 판별 가능한 대상**에 대한 결과다.

## 백업과 실행 자료

Git 제외 경로 `logs/console-recovery/2026-10-07/`에 보관한다. 디렉터리 권한은 700, 자료 파일은 600이다. 사용자 원문이 포함돼 있으므로 저장소에 커밋하지 않는다.

- `before.json`: 보정 전 대조 자료
- `plan.json`: 정확한 추가/수정 계획과 복구 시각
- `pre-apply.json`: 쓰기 직전 수정 대상 원본과 추가 대상
- `applied.json`: 커밋 결과 및 추가/수정한 ID 목록
- `after.json`: 커밋 후 별도 연결로 읽은 자료
- `verification.json`: 재대조 결과와 자료별 SHA-256
- `audit.cjs`, `apply.cjs`, `verify.cjs`: 실행·검증 절차. 적용 영수증이 있으면 재적용을 거부한다.

원복이 필요하면 `pre-apply.json`과 `applied.json`의 ID를 기준으로 이후 변경이 없는지 먼저 대조해야 한다. 사용자 카운터를 비롯한 다른 테이블을 백업 전체로 덮어쓰지 않는다.
